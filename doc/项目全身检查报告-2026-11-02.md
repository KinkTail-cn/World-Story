## P1：优先保护进度

### P1-01：F5 忽略蓝图库保存失败，仍提示保存成功

位置：`scripts/Main.gd:106`、`scripts/Main.gd:113`；`scripts/blueprint/BlueprintManager.gd:54`。

`save_progress()` 只检查世界文件的保存结果，调用 `blueprint_manager.save_json()` 后不检查返回值，直接显示“世界进度已保存”并返回 `true`。笔记随蓝图库保存，因此它们也受影响。蓝图库本身直接以 WRITE 模式覆盖文件，没有世界存档采用的临时文件替换保护。

复现：在隔离用户目录中把 `blueprints.json` 的目标路径设为目录，使蓝图库写入确定失败；添加一条笔记并调用实际 `save_progress()`。结果为：

```text
世界存档文件存在：true
蓝图库文件存在：false
save_progress()：true
提示：世界进度已保存
```

影响：玩家会误以为笔记和蓝图库已经落盘，退出后丢失本轮内容。遇到写入中断或空间不足时，蓝图库的直接覆盖也缺少保留旧文件的保护。

建议：检查每个持久化步骤的结果，明确提示哪部分保存失败；为蓝图库增加临时写入、错误检查和替换保护。若要求世界与蓝图库一致，增加保存批次标识或统一提交机制。验证时应同时覆盖“世界成功、蓝图库失败”和旧蓝图库仍可读取的情况。

### P1-02：坏存档仍显示“继续”，点击后静默创建新世界，备份不参与恢复

位置：`scripts/system/SaveSystem.gd:39`、`scripts/system/SaveSystem.gd:50`、`scripts/system/SaveSystem.gd:118`；`scripts/Boot.gd:47`；`scripts/ui/MainMenu.gd:87`。

存档存在性只依据文件是否存在。JSON 解析失败时，`load_game()` 返回空字典，`Boot._continue_game()` 随后按默认值开始新的创造模式无限世界。加载流程不尝试读取 `.bak`，也没有把“读取失败”与“新游戏空数据”区分开。

复现：在隔离目录写入损坏的主文件，并放入一份合法 `.bak`，刷新菜单后点击实际继续入口：

```text
“继续游戏”可见：true
load_game() 返回空字典：true
.bak 存在：true
最终启动：creative / infinite，loaded_data 为空
```

合法 JSON 的字段校验也不完整。例如对实际 Player 应用空的玩家字典，位置会从正常出生地变成 `(0, 0, 0)`，该格为基岩。当前正常保存文件包含这些字段，因此这一现象属于异常或不完整数据的恢复缺陷。

影响：玩家看起来执行了“继续”，实际进入新世界；如果随后按 F5，会覆盖主存档路径，且正常保存流程会移除 `.bak`，进一步降低找回旧进度的机会。

建议：加载接口返回明确的成功状态和错误原因；先验证结构、模式、坐标、物品和世界数据，再开始切换场景。主文件异常时验证并尝试恢复备份；无法恢复时留在菜单并展示错误。玩家字段缺失应保留安全出生位置，避免默认写入基岩内部。

## P2：功能、资源与体验

### P2-01：玻璃放入世界后失去透明效果

位置：`shaders/terrain.gdshader:7`；`scripts/world/VoxelWorld.gd:848`；对照 `scripts/content/BlockTextures.gd:47`。

手持和物品栏使用带透明设置的玻璃材质；世界网格统一使用地形 Shader，采样后只读取 `tex.rgb`，没有输出透明度。邻面剔除还把所有非空气方块统一视为不透明遮挡。

窗口复现：通过真实 `set_block()` 路径搭建 5 × 3 玻璃墙，后面放置红砖墙。玻璃完全挡住红砖，移除玻璃后红砖才可见。与背包中的透明玻璃预览存在明显不一致。

建议：区分不透明与透明网格/材质，分别处理透明度、深度和邻面可见性；同时验证“玻璃邻接普通方块”和“玻璃邻接玻璃”，避免只补 ALPHA 后出现缺面或排序问题。

### P2-02：手套“左右镜像”围绕一只手镜像，无法生成另一只手的对称设计

位置：`scripts/ui/BlueprintWorkshop.gd:1088`、`scripts/ui/BlueprintWorkshop.gd:1462`；`scripts/blueprint/BlueprintEquipment.gd:81`。

手套部位的局部原点是人物横坐标 `-0.3375`，镜像逻辑只把相对原点的 `center.x` 取负。人物中央的左右对称需要在人物坐标中镜像，再换回局部坐标。

复现：放置相对横坐标 `0.13` 的手套体素后点击真实镜像功能。两个体素在人物预览中的横坐标分别为：

```text
-0.2075
-0.4675
```

两个都在人物同一侧，窗口截图也确认了这一点。

建议：按部位原点换算到人物坐标，使用人物中轴镜像后写回局部坐标；针对手套以及其他带偏移原点的类别增加几何验证。

### P2-03：回收图纸无条件追加全局蓝图，相同设计反复进入蓝图库

位置：`scripts/Main.gd:251`、`scripts/Main.gd:257`；对照 `scripts/blueprint/BlueprintManager.gd:23`。

回收纸笔时直接向全局 `blueprints` 追加内容，没有使用蓝图库已有的同名同类别更新规则，也没有稳定设计 ID 或去重判断。

复现：三次回收携带相同名字、相同内容的图纸，全局蓝图库条目数依次变为 `1 → 2 → 3`。正常反复放置、回收同一份内容也会经过同一路径。

影响：蓝图库选择列表产生大量重复项，保存文件随操作次数增长；后续保存同名设计只更新第一个匹配项，其他旧副本还会保留。

建议：统一图纸导入和全局蓝图保存入口；明确“相同设计更新”与“另存副本”的规则，使用稳定 ID 或内容校验完成去重。

### P2-04：第一次打开工坊的未保存草稿，关闭再打开即丢失

位置：`scripts/ui/BlueprintWorkshop.gd:156`、`scripts/ui/BlueprintWorkshop.gd:166`；对照 `scripts/ui/BlueprintWorkshop.gd:1554`。

当 `manager.current` 为空时，`open()` 只创建工坊局部 `blueprint`，没有把它设为当前设计。第一次绘制后关闭再打开，会再次创建空对象。通过“新建设计”创建的草稿则会写入 `manager.current`，两条入口表现不一致。

复现：全新蓝图库打开 P 工坊，添加一个体素，关闭后重新打开，体素数由 `1` 变成 `0`，`manager.current` 仍为 `null`。

建议：统一初始化当前草稿；对关闭、切换已保存蓝图和新建设计设置明确的草稿保留规则。这里测试的是关闭重开丢失，不把尚未点击“保存蓝图”的内容等同于已经落盘的设计。

### P2-05：笔记界面宣称可编辑已有篇章，保存实际上追加一篇

位置：`scripts/ui/NotebookPanel.gd:17`、`scripts/ui/NotebookPanel.gd:30`；`scripts/blueprint/BlueprintManager.gd:46`；`scenes/NotebookPanel.tscn:264`。

“点击载入编辑”会把原笔记放入编辑器，但界面没有保留选中索引，`save_note()` 只执行 `notes.append()`。

复现：保存 `original note`，点击第一条、改为 `edited note`、点击保存，最终得到 `["original note", "edited note"]`，原记录没有被修改。

建议：区分新增与编辑状态，编辑时更新对应记录；保存后同步选中项。界面也应明确笔记按钮是否仅更新内存，以及何时写入磁盘，避免与 F5 保存规则混淆。

### P2-06：重新生成世界后，旧挖掘碎屑永久留在 Boot 场景中

位置：`scripts/player/Player.gd:597`、`scripts/player/Player.gd:612`、`scripts/player/Player.gd:644`；`scripts/Boot.gd:66`。

碎屑和命中火花被加入 `get_tree().current_scene`。从默认 Boot 入口运行时，这个节点是 Boot；碎屑的生命周期却由旧 Player 的 `debris` 数组更新。重新生成会释放旧 Player，但不会释放 Boot 下的碎屑。

复现：产生 9 个碎屑后立即重新生成，等待超过 1 秒——已超过正常 0.7 秒寿命——9 个碎屑仍然存在于 Boot 下。重复操作会继续累积。

建议：把临时世界效果放入当前 Main 或专用世界效果容器，随该局游戏统一释放；也可让效果自行计时销毁。验证必须从 Boot 默认入口执行，直接把 Main 作为当前场景会掩盖这个问题。

### P2-07：继续远处存档时，同步加载出生区块，随后才加载玩家所在区域

位置：`scripts/Main.gd:72`；`scripts/world/VoxelWorld.gd:143`、`scripts/world/VoxelWorld.gd:503`；`scripts/system/SaveSystem.gd:118`。

`load_data()` 固定对区块 `(1, 1)` 执行 `instant=true` 的 49 区块加载；Player 位置随后才恢复。初始预热协程也固定使用出生区块作为中心。

复现：保存玩家位置 `(400.5, 3.01, 400.5)` 后继续游戏，继续入口同步耗时 **448.865 ms**；函数返回时已有 49 个出生区块，玩家所在区块还没有加载。之后逐帧流式加载到玩家附近。

本次远处读档最终正常落在地面，最低脚部高度约 `3.000117`，没有据此认定发生穿地；已确认的问题是加载错误区域和额外同步开销。

建议：先读取存档位置，统一决定加载中心；把存档应用与初始加载合为一条可等待流程，等玩家附近碰撞完成后再交付控制。为加载工作设置时间预算，避免在进入场景的同步回调中生成整片视距。

### P2-08：区块生成扫描所有修改历史，世界越建越慢

位置：`scripts/world/VoxelWorld.gd:633`、`scripts/world/VoxelWorld.gd:639`；`scripts/world/VoxelWorld.gd:783`。

生成一个区块时，会遍历整个 `_modified_blocks`，再筛选属于当前区块的条目。即使修改都远离当前区块，仍然需要全部扫描。网格和三角网格碰撞也在主线程同步生成。

对同一个目标区块的人工压力样本：

| 全局修改历史 | 单次区块方块数据生成 |
| --- | --- |
| 0 条 | 3.760 ms |
| 10,000 条 | 4.946 ms |
| 100,000 条 | 18.192 ms |

这部分计时仅包含 `_generate_chunk_blocks()`，还没有计入该区块的网格、碰撞和渲染。其他短样本中，新区块完整创建约 6.6–11.3 ms，区块内部单格修改约 5.9–8.0 ms，区块角部修改会联动三个网格，约 12.6–13.5 ms。60 FPS 的整帧预算约 16.7 ms，不能仅按“每帧一个区块”保证稳定帧率。

建议：将修改记录按区块分桶，避免每次全局扫描；合并同帧同区块的多次重建。进一步优化时把纯数据和网格数组计算移到工作线程，节点及物理资源提交按主线程预算处理。保留压力测试用于观察建造规模增长后的表现。

### P2-09：加载遮罩显示期间，角色仍然接收移动输入并参与物理

位置：`scripts/Main.gd:67`、`scripts/Main.gd:142`；`scripts/ui/LoadingScreen.gd:94`；`scripts/player/Player.gd:270`。

加载界面没有控制 Player 的输入或物理启用状态，`loading_completed` 也未接入主流程。UI 遮罩能够接收鼠标事件，但玩家移动来自全局 `Input` 查询。

复现：新建无限世界后，在加载遮罩仍显示的前 8 个物理帧中按住 W，角色水平移动约 **0.187 m**，竖直移动约 **-0.140 m**。

影响：玩家会在看不到世界时移动；低帧率或较长加载时，这段不可见活动更明显。

建议：增加独立的加载状态，在附近世界及碰撞就绪后启用玩家控制；避免直接用全树暂停阻断加载任务本身。加载完成信号应参与控制权交付。

### P2-10：关键提示和部分工坊按钮对比度过低

位置：`scenes/HUD.tscn:25`、`scenes/HUD.tscn:359`；`scripts/ui/BlueprintWorkshop.gd:769`、`scripts/ui/BlueprintWorkshop.gd:791`。

真实窗口中，Toast 使用接近白色的文字配浅米色背景，欢迎和保存提示都很难辨认。工坊材料按钮将材料颜色继续调亮，又将未选中按钮整体压暗，部分材料名称和橡皮擦标签也接近背景色。

这会直接影响“保存失败”“背包已满”等重要反馈的可读性。建议为提示确定固定的深色文字/浅色背景组合，或相反；材料色用于色块、边框或图标，名称保持稳定对比。验收应包含默认窗口中的真实截图，而非只检查控件可见性。

### P2-11：游戏内指引展示尚未实现的能力

位置：`scripts/inventory/ItemCatalog.gd:260`、`scripts/inventory/ItemCatalog.gd:283`、`scripts/inventory/ItemCatalog.gd:299`；`scripts/ui/LoadingScreen.gd:13`；`scenes/HUD.tscn:629`。

当前 README 明确武器没有战斗结算、防具没有护甲结算、生存没有氧气和溺水机制；但游戏内仍显示“击退目标”、具体护甲加值和“留意氧气消耗”。加载提示还写着“在暂停菜单中保存”，实际暂停菜单只有继续、重新生成和退出。

建议：对当前无法生效的伤害、击退、护甲数值标注为计划值，或暂时收起；调整氧气提示，并让暂停菜单的保存指引与实际按钮一致。这里记录的是界面承诺与实现不一致，不把已经明确尚未开发的战斗、生存系统本身列为程序故障。

## P3：恢复可信的回归基线

### P3-01：BlocksSmoke 对不可见子控件的断言沿用旧结构

位置：`tests/BlocksSmoke.gd:210`；`scripts/ui/InventoryPanel.gd:163`。

测试断言 `not panel.crafting_box.visible`，当前界面通过父级 `craft_section` 控制显示。实际探针结果：

```text
creative_section.visible = true
craft_section.visible = false
crafting_box.visible = true
crafting_box.is_visible_in_tree() = false
```

真实窗口也确认创造物品库正常显示、合成区没有露出。因此当前失败应归为测试断言过期，而非“创造背包把合成栏显示出来”。断言失败后该协程终止，后续全物品分类和世界放置检查没有运行，直到测试自己的超时才退出。

建议：使用 `is_visible_in_tree()` 验证用户实际看到的状态，并验证切回合成页后的显示；维护测试失败的即时退出或汇总机制。修复后应完整运行 BlocksSmoke，再运行统一脚本，重新建立全绿基线。
