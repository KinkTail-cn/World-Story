## 一、 个人开发核心策略：做减法与技术降维

个人全栈开发最大的制约是**个人精力与时间极度有限**。如果单人按照大厂团队的标准去死磕底层 C++ 原生扩展编译、端侧大模型环境配置与四大文明的海量美术建模，项目极易在半年内因疲惫而烂尾。

因此，个人开发必须奉行**“保住核心灵魂、善借开源外力、先验证后重构”**的极简生存法则：

```
					┌────────────────────────────────────────┐
					│      《World Story（世界物语）》       │
					│         个人全栈核心策略树             │
					└───────────────────┬────────────────────┘
			 ┌──────────────────────────┼──────────────────────────┐
			 ▼                          ▼                          ▼
	 【坚决保留的核心灵魂】      【前期大刀阔斧的减法】     【充分借力的开源轮子】
   ├── 微体素物理公式推导       ├── 暂缓 C++ 原生扩展编译  ├── Godot-Jolt 物理插件
   ├── 转动惯量与攻速耐力映射   ├── 语言模型先用词库替代   ├── 免费体素工具 MagicaVoxel
   ├── 接触压强与受力截面断裂   ├── 先做单势力与假人打靶   └── 假倒角边缘着色器
   └── 三视角统一平滑切换       └── 暂不做百人军团与多势力
```

### 1.1 坚决保留的“核心灵魂”（不可妥协）
* **规整方块沙盒循环**：瞄准、挖掘、掉落、拾取、放置必须形成稳定且可重复的基础循环。
* **清爽动漫视觉识别**：方块几何、纯净色彩、Toon 光照和清晰的交互反馈必须保持统一，不能回退到噪点像素风。
* **双视角与双端操作**：第一人称精密建造、第三人称探索，以及键鼠和触控输入都必须保持可用；上帝视角和远期微体素力学属于储备功能。

### 1.2 前期必须大刀阔斧“做减法”的模块
* **暂缓底层 C++ 原生扩展（GDExtension）**：
  * 前期不要碰 C++ 混合编译与环境配置！
  * 在原型期，使用纯 GDScript 配合平铺一维数组（Flat Array）完全足以驱动 $16^3 = 4096$ 体素的微观工坊运算。等玩法彻底验证好玩、大世界遇到性能瓶颈时，再考虑算法下沉。
* **端侧大语言模型（SLM）先用“规则模板词库”降维替代**：
  * 前期不要花数周时间去编译集成复杂的模型推理库；
  * 先用一套**基于力学数值条件的字符串插值规则模板库**（例如：检测到武器质心力矩大于阈值，触发“刻薄工匠”嘲讽台词），先跑通玩法与幽默交互闭环，后期有充裕精力再无缝接入真实本地模型。
* **世界观与文明势力大幅精简**：
  * 前期绝不铺开四大文明，**只做 1 个势力（甚至只做中立荒野 + 受击假人 + 1 种野生怪物）**，集中精力打磨单局破坏与战斗循环。

### 1.3 充分借力的开源与原生工具
* **物理引擎**：从 Godot 资产库一键启用 `Godot-Jolt` 官方插件，彻底解决原生物理穿模问题，无需手写 C++。
* **美术资产**：采用纯色材质调色板，配合一段简短的“假倒角着色器（Procedural Bevel Shader）”，即使只有简单的立方体，也能渲染出高品质手工玩具沙盘质感。

## 二、 四阶段滚雪球迭代路线 (MVP 驱动)

个人开发最需要**“高频即时正反馈”**，拒绝数月见不到画面的黑盒开发，推荐按以下四阶段层层推进：

```
[第 1 阶段：核心玩具验真 (3~4 周)]
  └── 纯 GDScript 做出 16³ 工作台 ➔ 拼装武器 ➔ 受击假人打靶 ➔ 验证力学手感
			│ 确认好玩、有爽感
			▼
[第 2 阶段：破坏与三视角闭环 (3~4 周)]
  └── 平地测试场 ➔ 挥刀劈碎方块墙 ➔ 武器受力过载折断 ➔ 一键平滑切换三视角
			│ 形成完整的单局破坏乐趣
			▼
[第 3 阶段：简易生存与敌人涌现 (4~6 周)]
  └── 采集木石材料 ➔ 状态机敌人追击 ➔ 敌人根据武器重心触发吐槽 ➔ 简易基地搭建
			│ 具备最基本的生存游戏框架
			▼
[第 4 阶段：底层加固与 Steam 试玩版 (4~6 周)]
  └── 引入多线程优化 ➔ 完善场景 UI 与音效 ➔ 录制宣传片并在 Steam 上架试玩页面
```

### 2.1 第 1 阶段：核心玩具验真（3 ~ 4 周）
* **开发目标**：不写主菜单、不画精美角色，只在一个空场景中做好“微体素工作台”。
* **具体任务**：
  1. 搭建 $16 \times 16 \times 16$ 的工作台网格，支持鼠标点击放置/拆除木头、石头、生铁方块；
  2. 编写力学评估脚本（`PhysicsEvaluator.gd`），遍历计算方块总质量与三维质心坐标；
  3. 将质心到手柄的距离直接映射为挥动动作的前摇速度与耐力消耗；
  4. 场景内放置受击假人，测试不同重心形态武器的挥打手感与击退距离。
* **阶段验收标准**：即使全是灰模方块，你自己也愿意在工作台里反复拼装 10 把不同的奇葩武器去砍假人，并觉得很有趣。

### 2.2 第 2 阶段：破坏与三视角闭环（3 ~ 4 周）
* **开发目标**：跑通“自制武器破坏世界”与“视角的自由切换”。
* **具体任务**：
  1. 搭建微型单区块方块墙，自制武器击中方块时扣除方块生命值并产生碎裂效果；
  2. 实现图论最小割算法：当自制武器撞击超硬材质时，计算结构中最薄弱的体素颈缩处，即时折断为两截并生成掉落物理刚体；
  3. 编写统一的摄像机脚本（`CameraRig.gd`），按下鼠标滚轮在第一人称、第三人称与上帝视角间平滑插值过渡。
* **阶段验收标准**：能在三视角下游刃有余地观察、挥砍并砸碎方块墙。

### 2.3 第 3 阶段：简易生存与敌人涌现（4 ~ 6 周）
* **开发目标**：从“独立玩具”进化为“微型可玩游戏”。
* **具体任务**：
  1. 制作一个简易巡逻敌人，挂载有限状态机（巡逻、追逐、攻击、受击硬直、死亡）；
  2. 建立规则词库：敌人发现玩家武器后，提取其质心比率与材质，在头顶弹出幽默嘲讽台词气泡；
  3. 支持在地面上批量放置方块，搭建简易防守木栅栏或石墙；
  4. 引入木材与矿石的简单采集与掉落。
* **阶段验收标准**：完成“采矿 ➔ 拼刀 ➔ 战胜嘲讽你的怪物 ➔ 砌墙防御”的单局完整循环。

### 2.4 第 4 阶段：底层加固与试玩版发布（4 ~ 6 周）
* **开发目标**：达到对外发布试玩展示的商业水准。
* **具体任务**：
  1. 材质应用假倒角着色器与微表面高光，配置柔和的环境光照与体积雾，极大提升画面质感；
  2. 检查并清理物理处理中的临时内存分配，确保长时间挥砍战斗不发生卡顿；
  3. 导出可独立执行的程序包，录制实机玩法短视频，在社交媒体或 Steam 上架试玩页面收集反馈。

## 三、 Godot 4.x 单人架构与代码纪律

一个人做独立开发，最怕三个月后自己看不懂自己写过的代码。必须严格遵守以下代码与架构准则：

### 3.1 强制组件化拆分（拒绝上帝类）
坚决杜绝把上千行代码堆砌在 `Player.gd` 中。通过功能组件组合挂载：
* `HealthComponent.gd`：负责生命值增减与死亡信号派发；
* `WeaponHolderComponent.gd`：负责武器插槽挂载、挥动控制与碰撞盒激活；
* `StaminaComponent.gd`：负责挥舞与机动的耐力管理；
* 玩家根节点仅作为状态调度器，组件之间只通过信号联动。

### 3.2 坚持数据驱动配置（Resource）
* 所有体素材料（松木、铁矿、黑曜石等）必须继承 `Resource`，在编辑器中创建独立的数据文件（`.tres`）；
* 属性参数（密度、硬度、韧性、材质颜色）全部可视化填写，严禁在业务代码中硬编码多层配置字典。

### 3.3 场景化 UI 与响应式绑定
* 严禁在脚本中动态写 `Button.new()` 拼装复杂界面，所有 UI 一律使用 `.tscn` 场景制作；
* UI 节点绝不直接读取业务层的内部变量，仅通过监听全局事件总线（`SignalBus`）的信号来触发自身刷新。

### 3.4 统一输入映射（InputMap）
* 严禁在脚本中判断具体的物理键值；
* 所有交互必须在 Godot 项目设置中配置语义化动作名（如 `move_forward`、`interact`、`switch_view`），代码中统一通过 `Input.get_vector()` 或 `Input.is_action_just_pressed()` 读取。

### 3.5 运行期零堆内存分配（Zero-Allocation）
* 在 `_physics_process(delta)` 物理循环中，严禁动态实例化 `PhysicsRayQueryParameters3D.create()` 或新建临时数组/字典；
* 所有复用参数在脚本顶部 `@onready` 初始化，循环中只修改属性，杜绝垃圾回收引起的帧率抽搐。

## 五、 个人时间管理与“全栈主题日”节奏

没有制作人催促进度时，个人开发者最容易陷入拖延或推倒重来的死循环。建议采用**“全栈主题日”**的日程管理法：

* **周一至周三（核心工程硬仗）**：
  * 大脑认知状态最佳时期，专注攻克物理公式计算、射线检测、装配网格与控制状态机；
* **周四（视觉与美术包装）**：
  * 写着色器、调环境灯光、用体素工具拼几个新构件，给游戏“换新装”，获取强烈的视觉正反馈；
* **周五（打击感与手感调优）**：
  * 配齐挥空、击中木头/石头的音效，微调屏幕震动与攻击顿挫感（Hit-stop）；
* **周末（沉浸式实机试玩）**：
  * 彻底关闭代码编辑器，像普通玩家一样纯玩自己的游戏 30 分钟；
  * 记录所有不流畅、反直觉的体验细节，同步写入项目根目录下的 `开发日志.md`，作为下周的首要修复目标。

## 六、 个人独立开发常见陷阱与避坑准则

1. **陷阱一：过早优化（Premature Optimization）**
   * *表现*：游戏还没跑通，就花三周时间用 C++ 优化一个当前只有几千次运算的算法。
   * *规避*：始终遵循“先跑通、再验证、有瓶颈才优化”。只要当前帧率在 60 帧以上，就把时间留给打磨核心玩法。
2. **陷阱二：无限扩张的世界体量（Feature Creep）**
   * *表现*：核心武器手感还没做好，就迫不及待构思四大文明、科技树流转、多人联机网络同步。
   * *规避*：严格恪守“阶段 1 核心玩具”未通过前，禁止编写任何宏观大世界或科技树代码。
3. **陷阱三：闭门造车数年不发声**
   * *表现*：总觉得“等我做完美了再给别人看”，结果做了一年发现核心概念根本吸引不了人。
	* *规避*：一旦第 1 阶段工作台跑通，就录制 15 秒短视频（展示“拼一把奇葩外形武器去砍假人、测质心”的实机过程）发到社交平台，检验核心概念的市场吸引力。

## 七、 当前工程运行与测试手册

本项目当前是 Godot 4.x 原型工程，启动场景由 `project.godot` 指向 `ui/main_menu/MainMenu.tscn`。代码、场景和测试都在同一个工程内维护，测试场景不会自动成为游戏启动入口。

### 7.1 日常运行流程

1. 使用 Godot 4.x 编辑器打开项目根目录，不要单独打开 `doc/` 目录。
2. 运行项目，确认首屏进入主菜单；若直接进入测试场景，说明运行配置被临时修改，应恢复主场景。
3. 桌面端默认使用 `WASD` 移动、空格跳跃、`Shift` 冲刺、鼠标旋转视角、左键破坏、右键放置、`F` 坐椅子/凳子或起身、`V`/`F5` 切换视角、`B`/`E` 打开背包、`ESC` 打开菜单。坐下交互优先检查准星，若家具腿间空隙导致射线未命中，则自动搜索玩家附近的椅子或凳子。
4. 需要模拟触控时使用 `F8` 切换触控 HUD；真实移动端以 `OS.has_feature("mobile")` 自动显示触控层。
5. 存档只在局内点击“保存世界”后正式创建。创建新游戏后直接退出不应产生完整存档。

### 7.2 测试场景

| 场景 | 验证范围 |
| :--- | :--- |
| `tests/TestSaveLifecycle.tscn` | 新建会话不提前落盘、主动保存后生成 `meta.json` 和 `data.json` |
| `tests/TestGameModes.tscn` | 生存/创造背包规则、物品消耗、存档模式恢复 |
| `tests/TestPauseMenu.tscn` | 暂停菜单、ESC 层级返回、设置保存和信号切换 |
| `tests/TestBlockIcons.tscn` | 方块图标缓存、快捷栏结构、背包槽位和拖拽虚影节点 |
| `tests/TestTables.tscn` | 家具几何、长桌占格、坐垫在整格/半格支撑上的高度、放置及存档恢复 |
| `tests/TestSitting.tscn` | 坐下交互动作及坐垫在整格/半格支撑上的人物高度 |

运行测试时，在 Godot 编辑器中打开对应 `.tscn` 并运行，或使用命令行执行对应场景。测试脚本会在结束时主动退出；若出现断言失败，应先修复第一个失败项，再继续处理后续错误。

### 7.3 质量记录要求

“测试 100% 通过”只允许在实际运行对应测试场景后写入开发日志。人工试玩、桌面触控模拟和真实手机测试必须分别记录，不能用自动化断言替代。每个版本至少记录：引擎版本、运行平台、测试场景、结果、已知限制和未处理问题。

### 7.4 存档与设置路径

存档目录为 `user://saves/<folder_name>/`，包含 `meta.json` 和 `data.json`；全局设置位于 `user://settings.cfg`。调试存档问题时优先通过游戏内存档列表删除，不要手工删除用户目录中的未知文件。

### 7.5 文档维护顺序

实现变更按以下顺序同步：先更新代码注释或场景结构，再更新本指南和权威基准中的当前实现基线，最后在根目录 `开发日志.md` 追加一条可验证记录。早期全案中的宏大系统描述只作为历史设计库，不作为当前实现验收标准。

### 结语

《World Story（世界物语）》对于个人独立开发者而言，是一座巨大的宝藏：**它不依赖大量繁琐的手绘美术资产，而是纯粹依靠离散几何与力学物理的自洽，源源不断地涌现出玩家自创的乐趣。**

只要保持克制与专注，以最纯粹的 GDScript 先把能够**“移动、瞄准、敲碎、拾取、放置、保存并重新载入”的动漫方块沙盒闭环**做稳定，项目就有了可持续扩展的基础。
