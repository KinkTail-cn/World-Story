# 重建基线与文档优化建议

## 当前问题

1. 开发日志记录了大量已经完成的功能，但工作区没有对应的 Godot 工程文件，日志不能作为实现证明。
2. 权威基准方案、历史全案和开发日志混合描述，读者容易把远期设计误认为当前需求。
3. 方块 ID 在家具、水体和物品系统中逐渐扩展，但没有统一的内容注册协议，后期 Mod 容易出现 ID 冲突。
4. “自动化测试 100%”没有统一测试命令、引擎版本、平台和测试输出，无法复现验收结果。
5. 当前文档缺少明确的版本迁移策略、存档兼容策略、Mod 生命周期和性能预算。

## 统一规则

1. 以实际可运行代码为实现事实来源，开发日志只记录可复现的变更。
2. 权威基准只保留当前版本目标、参数和验收口径；远期系统全部放入历史设计库。
3. 内容使用注册表和数据文件扩展。核心逻辑只依赖稳定 ID 和能力接口，不直接依赖具体 Mod 文件路径。
4. 每个版本记录 Godot 版本、平台、启动场景、测试场景、结果和已知限制。
5. 存档携带 schema_version、world_seed 和内容注册表版本；加载时先迁移，再应用数据。
6. 每一阶段只增加一个玩家可感知的完整闭环，完成后再扩大地图和系统数量。

## 当前重建阶段

当前先交付可运行核心切片：程序化动漫方块地形、第三人称移动、跳跃、准星选中、破坏、放置和内容注册表。下一阶段再接入掉落物、背包、存档和移动端输入，并为每个系统增加独立验收场景。
